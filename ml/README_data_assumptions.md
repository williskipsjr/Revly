# Synthetic data assumptions — P(success) model (Phase 3)

**Everything here is simulated.** There is no real Razorpay data anywhere in this repository.
The training set is generated by a documented synthetic process (`generate_synthetic.py`). Every
result carries the standing disclaimer:

> These results demonstrate performance in a simulated environment and do not represent real
> Razorpay customer behaviour.

The point of this model is **not** modelling sophistication — it is to replace the Phase-2
hand-set `P(success)` heuristic with an *interpretable, data-fit* estimate so the economic layer
(ERV) ranks actions from learned coefficients rather than guesses (PLAN.md §5, §7). It is a
plain logistic regression, trained with numpy in a few dozen lines, and nothing more.

## What the model estimates

`P(success | context, action)` — the probability that a given recovery **action** recovers a
given failed payment. This is a **separate code path** from diagnosis and from LLM confidence
(PLAN.md §7): it consumes only structured context features, never diagnosis text. `no_action` is
not modelled — it recovers nothing by definition (P = 0), the clean ERV baseline.

## Features (PLAN.md §5)

| Feature | Type | Notes |
|---|---|---|
| `prior_attempts` | numeric (standardized) | provider prior attempts + retries already dispatched |
| `amount_tier` | numeric (standardized) | `floor(log10(amount_paise + 1))`, clamped 0..8 |
| `method` | one-hot | card, upi, netbanking, wallet, emi, other |
| `action` | one-hot | retry, delayed_retry, alt_method, payment_link, notify, escalate |

`ml/features.py` is the single source of truth for featurization; the Go engine
(`decision-engine/internal/successmodel/model.go`) re-implements exactly this, and the
`test_vectors` embedded in the exported artifact are reproduced by the Go tests to guarantee the
two agree.

**Deliberately omitted — elapsed time-since-failure.** PLAN.md §5 lists it as a candidate
feature, but the Phase-2 pipeline decides synchronously at t ≈ 0, so elapsed wall-clock time
carries no signal at decision time. The benefit of *waiting* is instead captured by the
`delayed_retry` action itself. This is an MVP simplification, not a modelling claim.

## Synthetic generative process (the "ground truth")

For each row we draw `method`, `action`, `prior_attempts`, and `amount`, then compute a latent
recovery probability and sample a Bernoulli label:

```
p_true = BASE[action] · METHOD_MULT[method] · DECAY^prior_attempts · (1 − 0.03·(amount_tier − 3))
label ~ Bernoulli(clip(p_true, 0.01, 0.98))
```

- `BASE` (intervention base rates) is intentionally **different from the Phase-2 heuristic**. In
  particular the synthetic world says a fresh **payment link** recovers more than an alternative
  method (`payment_link` 0.63 > `alt_method` 0.50), whereas the Phase-2 heuristic guessed the
  reverse. Because both are candidate actions for an *expired-method* diagnosis, the trained model
  selects a **different action** than the heuristic on the same event — the concrete proof that a
  data-fit model changes decisions (asserted in the Go pipeline/store tests).
- `DECAY = 0.82`: each prior failed attempt lowers recovery probability, so `P(success)` is
  monotonically non-increasing in `prior_attempts` (asserted).
- Larger amounts are modestly harder to recover (small negative amount effect).

These are assumptions, not observations. They are plausible and internally consistent, nothing
more.

## Train / validation / held-out separation (no leakage)

`train_success_model.py` splits the generated data **70 / 15 / 15**:

- **Standardization statistics** (feature means/stds) are fit on the **training** split only.
- **Model weights** are fit on the **training** split only.
- **L2 strength** is selected on the **validation** split.
- The **held-out** split is touched exactly once, for the final metrics report, and never
  influences fitting or selection.

This held-out split is the model's own internal test set. It is **distinct** from the Phase-9
simulation harness's evaluation population (`../sim/`), which is generated separately, with a
different seed, and is never seen here.

## Reproducing

```bash
pip install -r ml/requirements.txt          # numpy only
python -m ml.train_success_model            # writes artifacts/success_model.json + metrics.json
python -m unittest ml.tests.test_success_model
```

Training is deterministic (fixed seed), so the committed
`artifacts/success_model.json` is reproducible. The Go decision engine loads that artifact at
startup (`SUCCESS_MODEL_PATH`); if it is absent, the engine falls back to the Phase-2 heuristic
and logs the fact — the pipeline never stalls on a missing model.

## Metrics (held-out)

See `artifacts/metrics.json` for the current run (AUC, log-loss, Brier, the validation selection
grid, and a calibration table). On this noisy synthetic set the model is meaningfully better than
random and well-calibrated (mean predicted ≈ empirical positive rate); it makes **no** claim to
production-grade performance.
